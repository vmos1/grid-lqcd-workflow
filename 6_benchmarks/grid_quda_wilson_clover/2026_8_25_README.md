# Grid versus QUDA Wilson and Wilson-clover benchmark

_(updated 2026-08-25 12:47 CDT)_

This benchmark tests—not assumes—the following causal claim:

> Stock Grid's Wilson-clover operator is slower than stock QUDA's, and lower operator throughput makes otherwise matched Wilson-clover CG solves slower.

The Wilson action is the control. A clover-specific conclusion requires Wilson to be comparatively close, a larger Wilson-clover gap, and solve time per iteration consistent with the preconditioned normal-operator measurements. Contrary outcomes must be reported as such.

This benchmark is intentionally separate from the Hasenbusch tuning studies.

## Evidence and timing boundaries

_(updated 2026-08-25 14:20 CDT)_

The study has three distinct measurements:

1. The shared executable gives Grid and QUDA identical gauge/spinor data, validates corresponding operations, times resident Grid operations, and times QUDA's host-pointer **public C API**.
2. Stock QUDA `dslash_test` supplies transfer-free resident-device timings from persistent QUDA fields/operators. Its generated gauge is suitable for the hot-gauge throughput study, not the physical-configuration solve.
3. The shared executable runs matched odd-checkerboard normal-equation CG solves and reports both end-to-end wall time and QUDA's internal solver time.

Do not call `dslashQuda`, `MatQuda`, `MatDagMatQuda`, or `cloverQuda` pure kernel timings: those public interfaces allocate/wrap fields, transfer host/device data, construct an operator, compute, and copy the output back. They are useful end-to-end measurements and numerical cross-checks. The resident QUDA result comes from stock `dslash_test`.

The central fixed-work comparison is the odd-checkerboard preconditioned normal operator

```text
M_pc = M_oo - M_oe M_ee^-1 M_eo
M_pc^dag M_pc
```

because CG applies it once per iteration. (For clover this is the asymmetric Schur form; for Wilson the diagonal block is a scalar and the distinction collapses — see "Matched conventions".) Dslash plus the local clover inverse partially decompose the aggregate operator cost.

The decomposition is deliberately incomplete on the QUDA side, and this is a QUDA limitation rather than a design choice. `ApplyClover` in `quda/lib/dslash_clover_helper.cu:25` opens with an unconditional `if (!inverse) errorQuda("Unsupported direct application")`, so there is no standalone direct clover multiply to time — `cloverQuda(..., inverse=0)` aborts the process. QUDA's direct clover term is reachable only *fused* into the stencil, since `ApplyWilsonClover` computes `A*x + kappa*D*in` in one kernel. The benchmark therefore pairs `pc_dslash`, `mat`, `normal_pc`, and `clover_inv`, but no `clover_mult`. Confirmed empirically on smoke job 57603507.

## Matched conventions

_(updated 2026-08-25 14:20 CDT)_

The two implementations use:

- Grid `SchurDiagMooeeOperator` on the odd checkerboard.
- An **action-dependent** QUDA `matpc_type` (see below).
- QUDA `QUDA_CG_INVERTER`, `QUDA_NORMOP_PC_SOLVE`, and `QUDA_MATPCDAG_MATPC_SOLUTION`.
- `kappa = 1 / (2(4 + mass))` and `QUDA_KAPPA_NORMALIZATION`.
- Identical double-precision Grid-generated source fields. The RNG stream is re-seeded per action, so the Wilson control and the clover case consume the same source fields operation-for-operation.
- Antiperiodic temporal fermion boundary conditions. Grid receives boundary phases `{1,1,1,-1}`; the QUDA bridge pre-bakes `-1` into temporal links on the global final time slice and preserves the validated QUDA boundary metadata.
- Native-MPI QUDA initialized with Grid's communicator and rank-coordinate callback.

### Preconditioned matrix type is action-dependent

_(updated 2026-08-25 14:20 CDT)_

```text
wilson: QUDA_MATPC_ODD_ODD             1    - kappa^2 D_oe D_eo
clover: QUDA_MATPC_ODD_ODD_ASYMMETRIC  A_oo - kappa^2 D_oe A_ee^-1 D_eo
```

This is forced, not chosen. `DiracWilsonPC::M` in `quda/lib/dirac_wilson.cpp` calls `errorQuda()` for anything but `QUDA_MATPC_EVEN_EVEN` or `QUDA_MATPC_ODD_ODD`: a Wilson diagonal block is the scalar `4 + mass`, so the symmetric/asymmetric distinction collapses and QUDA does not define the asymmetric enum for it. Both rows above are the operator that corresponds to Grid's `SchurDiagMooeeOperator` (`Moo - Moe Mee^-1 Meo`) on the odd checkerboard, and in both cases

```text
Mpc_quda = 2 kappa Mpc_grid
Mpc_quda^dag Mpc_quda = 4 kappa^2 Mpc_grid^dag Mpc_grid
```

so the same `2 kappa` / `4 kappa^2` corrections apply to both actions. The bridge divides `MatDagMatQuda` output by `4 kappa^2` for direct operator comparison and multiplies the solve right-hand side by `4 kappa^2`, yielding the Grid-convention solution. `perlmutter/run_benchmark.sh` passes the matching `--matpc odd-odd` / `--matpc odd-odd-asym` to stock `dslash_test`.

### Kappa normalization

_(updated 2026-08-25 14:20 CDT)_

The same kappa-normalization mismatch applies to the unpreconditioned full matrix and the local clover term, and the bridge corrects both the same way:

```text
M_quda = 2 kappa M_grid
A_quda = 2 kappa A_grid            (non-inverse clover diagonal)
A_quda^-1 = A_grid^-1 / (2 kappa)  (clover inverse)
```

`MatQuda`, `MatDagMatQuda`, and `cloverQuda` apply no `mass_normalization`-dependent rescale under `QUDA_KAPPA_NORMALIZATION` (confirmed by reading `quda/lib/interface_quda.cpp`: the `MatQuda`/`MatDagMatQuda` rescale branches fire only for `QUDA_MASS_NORMALIZATION`/`QUDA_ASYMMETRIC_MASS_NORMALIZATION`, and `cloverQuda` has no rescale branch at all), so their raw output is QUDA's kappa-normalized convention. The bridge's `apply_mat()` divides by `2 kappa`, and `apply_clover()` divides the non-inverse multiply by `2 kappa` and multiplies the inverse by `2 kappa`, before comparing against Grid's mass-normalized output.

### Dslash: the `pc_dslash` case is action-dependent too

_(updated 2026-08-25 14:20 CDT)_

`dslashQuda` hardcodes `pc = true`, so it always builds a *preconditioned* Dirac object and the operation it performs depends on the action:

```text
wilson: DiracWilsonPC::Dslash = ApplyWilson(..., kappa=0, ...)
          -> raw checkerboard hopping sum D_quda
clover: DiracCloverPC::Dslash = ApplyWilsonCloverPreconditioned(..., kappa=0, ...)
          -> A_quda^-1 D_quda
```

The shared operation label `pc_dslash` therefore means raw checkerboard `D` for Wilson and `A^-1 D` for clover. It is not a claim that the two actions perform the same sub-operation. Grid mirrors the split exactly: `DhopOE` alone for Wilson, `MooeeInv` composed after `DhopOE` for clover.

Neither QUDA path rescales for `mass_normalization` (`dslashQuda`'s `blas::ax` branch fires only for staggered/asqtad dslash types), so the raw output is in QUDA's own convention and **does** need converting. Grid imports the hopping links pre-scaled by `-1/2` (`WilsonFermionImplementation.h`: `HUmu = _Umu * (-0.5)`) while QUDA's `D_quda` is the bare sum, and Grid's clover diagonal carries `diag_mass = 4 + mass` with no kappa in it (`WilsonCloverFermionImplementation.h`), giving

```text
D_grid = -0.5 D_quda
A_quda = 2 kappa A_grid
A_grid^-1 D_grid = (2 kappa A_quda^-1)(-0.5 D_quda) = -kappa A_quda^-1 D_quda
```

so `apply_pc_dslash()` multiplies QUDA's output by `-0.5` for Wilson and by `-kappa` for clover. These two identities are the same ones that make `M_quda = 2 kappa M_grid` hold, so they are not an independent assumption. The runtime correctness gate remains the authority: no timing is collected for an operation whose two sides disagree.

## Inputs and precision modes

_(updated 2026-08-25 12:47 CDT)_

Use both inputs:

- A deterministic hot SU(3) gauge for portable smoke tests and fixed-work measurements.
- `data/cl21_48_96_b6p3_m0p2416_m0p2050-djm-3_cfg_2000.lime` for reported solve behavior.

Physical parameters:

```text
lattice: 48.48.48.96
process grid: 1.2.2.4 (16 ranks/GPUs, 4 nodes)
csw: 1.20536588031793
masses: -0.2416 and -0.1870
```

Precision modes:

- `strict`: double precise, double sloppy, `QUDA_RECONSTRUCT_NO`. This is the causal implementation comparison.
- `production`: double precise, single sloppy, `QUDA_RECONSTRUCT_12`. This is an application-performance comparison, not strict kernel isolation.

Grid remains double precision in both modes.

## Run protocol

_(updated 2026-08-25 13:16 CDT)_

`perlmutter/run_benchmark.sh` is allocation-neutral: invoke it only inside an already approved Slurm allocation. It does not call `salloc` or `sbatch`, and it fails immediately when `SLURM_JOB_ID` is absent.

One-GPU smoke example:

```bash
MODE=shared INPUT=hot ACTION=both PRECISION=strict \
LATT=8.8.8.16 MPI=1.1.1.1 SAMPLES=2 WARMUPS=1 REPETITIONS=2 SOLVE_REPEATS=2 \
./6_benchmarks/grid_quda_wilson_clover/perlmutter/run_benchmark.sh
```

Resident-device QUDA companion examples use stock `dslash_test` and its generated hot gauge. Run one action and one operator per invocation; `DTEST_OP` is `dslash`, `mat`, or `normal_pc`. For `ACTION=clover`, the runner passes both `--clover-csw` and `--compute-clover true`, so QUDA constructs the clover field from that gauge rather than benchmarking the stock test's default unrelated random host clover field:

```bash
MODE=dslash INPUT=hot ACTION=wilson DTEST_OP=normal_pc PRECISION=strict \
LATT=48.48.48.96 MPI=1.2.2.4 NODES=4 NTASKS=16 NTPN=4 MASS=-0.2416 \
./6_benchmarks/grid_quda_wilson_clover/perlmutter/run_benchmark.sh

MODE=dslash INPUT=hot ACTION=clover DTEST_OP=normal_pc PRECISION=strict \
LATT=48.48.48.96 MPI=1.2.2.4 NODES=4 NTASKS=16 NTPN=4 \
MASS=-0.2416 CSW=1.20536588031793 \
./6_benchmarks/grid_quda_wilson_clover/perlmutter/run_benchmark.sh
```

In `MODE=dslash`, `strict` maps to double/reconstruct-18. `production` maps to a separate single/reconstruct-12 fixed-work run; stock `dslash_test` does not execute a double-precise/single-sloppy mixed operator. Its timing is resident-device and therefore must not be paired directly with the shared harness's QUDA public-API time.

Physical strict solves must be run separately at both masses:

```bash
MODE=shared INPUT=physical ACTION=both PRECISION=strict \
LATT=48.48.48.96 MPI=1.2.2.4 NODES=4 NTASKS=16 NTPN=4 MASS=-0.2416 \
./6_benchmarks/grid_quda_wilson_clover/perlmutter/run_benchmark.sh

MODE=shared INPUT=physical ACTION=both PRECISION=strict \
LATT=48.48.48.96 MPI=1.2.2.4 NODES=4 NTASKS=16 NTPN=4 MASS=-0.1870 \
./6_benchmarks/grid_quda_wilson_clover/perlmutter/run_benchmark.sh
```

Use a dedicated `QUDA_RESOURCE_PATH`. The provenance records whether the cache directory began empty or seeded. Discard the first tuning solve; only zero-guess repeats after it belong in warm timing summaries.

Run in this order:

1. Small one-GPU hot-gauge correctness smoke.
2. Saturated one-GPU hot-gauge fixed-work benchmark and strict CG.
3. Four-GPU scaling at fixed local volume.
4. Sixteen-GPU physical strict solves.
5. Production-like mode only after strict validation.
6. Optional multigrid only after the Wilson/Wilson-clover CG result is complete.

Every allocation or `sbatch` submission requires separate approval.

## Correctness gates

_(updated 2026-08-25 14:20 CDT)_

Do not use timing data unless the corresponding numerical validation passes. Required checks are:

- Exact gauge and full/red-black spinor conversion round trips, executed at program startup; the red-black check also compares Grid's odd-checkerboard ordering with the odd slab produced by the explicit QUDA EO permutation.
- Paired Dslash, full matrix, local clover inverse, and preconditioned normal-operator relative L2 errors. (There is no paired direct clover multiply; QUDA does not expose one — see "Evidence and timing boundaries".)
- An independently evaluated Grid-Schur relative residual for each backend's returned solution—not only the solver-reported residual.
- Grid-versus-QUDA solution difference at the requested tolerance.
- Solve time per iteration consistent with the fixed-work normal-operator ratio.

A failure in any of the above aborts the run before timing is collected.

### Iteration counts and attribution

_(updated 2026-08-25 14:20 CDT)_

Iteration equality is treated as an **interpretation** gate, not a correctness gate. Grid's `ConjugateGradient` and QUDA's CG do not use identical stopping arithmetic—QUDA applies reliable updates at `reliable_delta`—so a small difference is expected in double precision and does not indicate a wrong operator. The operator equality checks above already cover correctness.

The harness therefore records, for every measured repeat and each backend, the iteration count, the solver-reported residual, and an independently evaluated Grid-Schur residual of that repeat's own returned solution. It then computes the relative span of iteration counts across both backends and all repeats and compares it against `--benchmark-iteration-tolerance` (default `0.02`; `ITERATION_TOLERANCE` in the runner). The result is emitted as `attributable_to_operator_throughput`.

When that flag is false, `summarize.py` annotates the solve ratio as `NOT attributable` in the table and lists the pair under a "Solve-ratio attribution" section. A record with no flag at all is reported as `attribution unknown`—absent evidence is never treated as attribution evidence. In either case, report convergence and throughput separately rather than quoting the ratio as a kernel result.

Do not proceed to multi-GPU if either one-GPU action fails. Do not make a clover-specific claim unless the Wilson control supports it. Never ratio Grid's resident operation timing against QUDA public-API timing as though both had the same setup/transfer boundary.

## Outputs and summary

_(updated 2026-08-25 14:20 CDT)_

Each run writes outside the repository under a flat dated run directory:

```text
runs/2026_8_25_grid_quda_wilson_clover/<run-id>/
├── provenance.env
├── records.jsonl
├── shared.log or dslash.log
└── quda_resource/
```

Summarize shared-harness JSONL files, stock `dslash_test` logs, or both together:

```bash
python3 6_benchmarks/grid_quda_wilson_clover/scripts/summarize.py \
  /path/to/run-a/records.jsonl /path/to/run-b/records.jsonl \
  --dslash-log /path/to/run-c/dslash.log /path/to/run-d/dslash.log \
  -o /path/to/summary.md
```

The two input kinds render as separate tables and are never mixed into the same ratio: the shared-harness table pairs `grid`/`quda` records case-by-case, while `--dslash-log` output gets its own "resident-device, separate binary" table with its own `benchmark`/`verify` gtest status and its own CPU-reference `deviation`, explicitly labeled as not comparable to the shared harness's `public_api_end_to_end` QUDA timing. `--dslash-log` parsing is a best-effort regex match against `quda/tests/dslash_test_utils.h`'s `printfQuda` formats and gtest's own `[ RUN/OK/FAILED ]` markers (see `scripts/summarize.py`'s `parse_dslash_log`). The binary and CLI have been validated without a GPU, but the parser still requires a spot-check against the first real GPU log.

The summarizer exits nonzero when a timing/solve group has a failed or missing correctness record, or a `dslash_test` log has a non-`OK` benchmark/verify status, and reports the timing statistic actually present (`mean`, `median`, or a single value) rather than silently calling a mean a median. Keep setup, upload, autotuning, public-API, and resident-device results visibly separate in any final report.

Solve records carry per-repeat arrays (`sample_seconds`, `iterations_all`, `true_residual_all`, `independent_residual_all`) alongside the aggregates, so a run whose repeats disagree cannot be read as a single clean number. The scalar `iterations` is the per-repeat median and is displayed with a `varies min-max` annotation whenever `iterations_constant` is false; `true_residual` and `independent_residual` are the **worst** value over the measured repeats (`residual_scope: max_over_measured_repeats`), never the warm correctness solve's. The warm solve's own residuals and iteration counts stay on the `kind: correctness` record with `phase: warm`. `s_per_iteration_median` is the harness's per-repeat median of seconds-per-iteration; the summarizer prefers it over dividing aggregates.

## Interpretation

_(updated 2026-08-25 14:20 CDT)_

Evidence supports the proposed explanation only if all of the following hold:

1. Strict Wilson-clover resident `M_pc^dag M_pc` is materially slower in Grid than QUDA.
2. The strict Wilson control has a clearly smaller gap, supporting a clover-specific diagnosis.
3. Matched solves converge to independently verified residuals and the harness marks the pair `attributable_to_operator_throughput`.
4. The solve-time-per-iteration ratio agrees with fixed-work normal-operator timing.

If Wilson has a comparable gap, the result instead points to a broader Wilson/Dslash or framework implementation difference. If iteration counts differ, separate convergence from throughput. If only public-API timing differs, investigate transfer/setup boundaries before drawing a kernel conclusion.

Multigrid is a later algorithmic comparison and must not be folded into the Wilson-clover kernel claim.
